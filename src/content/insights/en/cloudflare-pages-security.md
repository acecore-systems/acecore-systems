If CSP or cache settings on Cloudflare Pages do not appear to take effect, first check whether the response is for a static asset or a Pages Function. This article explains where `_headers` and a Function's `Response` apply, where to find the current configuration, and what to verify after deployment. Check the headers of error responses as well as successful responses to help identify missing configuration after adding an API.

This article records the March 2026 move of the contact form to an external service and the return to static delivery on Cloudflare Pages. The site configuration has since changed. **As of September 2026, the Acecore corporate site uses Pages Functions alongside static pages** for contact, comments, search, AI assistance, and CMS APIs. The sections below explain the reasons for the earlier choice and the boundaries of header configuration that remain relevant.

## How do Cloudflare Pages headers differ for static and Functions responses?

`public/_headers` applies to **static asset responses served by Pages**. [Cloudflare Docs' Headers source](https://github.com/cloudflare/cloudflare-docs/blob/production/src/content/docs/pages/configuration/headers.mdx) explains that `_headers` rules apply to static asset responses. [Cloudflare Pages: Headers](https://developers.cloudflare.com/pages/configuration/headers/) also says that these rules do not apply to responses generated by Pages Functions, even when the URL pattern matches. Set the CORS, cache, and security headers needed for API responses on the Function's `Response`.

So, writing `_headers` once does not necessarily affect every page and API on a site. Check the actual response headers for static HTML and `/api/*` separately.

## Where can you check the current header configuration?

The [current `_headers` file](https://github.com/acecore-systems/acecore-net/blob/main/public/_headers) sets HTML to revalidate and hashed `_astro/` assets to use long-term caching. The CMS has a separate CSP from regular pages, and `X-Frame-Options` is `SAMEORIGIN`. Do not copy the old article's `form-action https://ssgform.com`, one-hour HTML cache, or `DENY` as current values.

Check the [Pages Functions code](https://github.com/acecore-systems/acecore-net/tree/main/functions) for current dynamic routes. Review the external domains allowed by CSP against the scripts, images, frames, and network requests actually used. Do not copy the settings unchanged to another site.

## What should you check after deployment?

The corporate site publishes `main` through GitHub-connected Cloudflare Pages. The [current Node version](https://github.com/acecore-systems/acecore-net/blob/main/.node-version) is recorded in `.node-version`, the build steps are in `package.json`, and CI checks the build with `npm run build`. The March 2026 table stating “Node.js 22 / npx astro build” is not the current publishing procedure.

When checking a deployment, review the PR preview, the `main` build, the Pages production deployment, and the headers and body at the public URL separately. [Cloudflare Pages' Headers documentation](https://developers.cloudflare.com/pages/configuration/headers/) describes the `_headers` configuration.

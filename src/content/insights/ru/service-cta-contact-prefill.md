> **Дополнение за 2026 год, 9-й месяц:** примеры `ServiceSectionActions` и `service=web` ниже фиксируют конфигурацию, использовавшуюся на официальном сайте Acecore в 2026 году, в 6-м месяце. В текущей Acecore Systems CTA на [странице подробного описания услуг](https://github.com/acecore-systems/acecore-systems/blob/main/src/components/ServiceDetailPage.astro) добавляет `category`, `service`, `from`, `entry`, а [форма обращения](https://github.com/acecore-systems/acecore-systems/blob/main/src/pages/contact.astro) проверяет короткий service key и предварительно заполняет тип обращения и тему. Сейчас также используются hidden-поля для аналитики и интеграции, поэтому не копируйте описанное ниже решение «не использовать hidden-поля» как актуальную спецификацию. Принцип не доверять значениям URL и сопоставлять их с вариантами выбора на стороне формы по-прежнему актуален.

Когда пользователь, прочитав страницу услуги, думает: «Хочу обратиться с вопросом именно по этому», простая отправка в форму обращения приводит к потере части контекста.

В форме пользователю приходится заново выбирать тип услуги и самостоятельно вводить тему. Получателю тоже трудно понять, идет ли речь о веб-разработке, эксплуатации серверов или Aceserver, пока он не прочитает текст обращения.

На сайте Acecore мы улучшили этот путь с помощью [PR по передаче целевой услуги от CTA к форме обращения](https://github.com/acecore-systems/acecore-net/pull/100). В этой статье мы рассматриваем его не только как запись о реализации на Astro, но и как схему проектирования пользовательского пути, которую можно применить на других сайтах.

## Проверка предварительного заполнения формы с одной CTA

Проверьте действия с корректным service key, неизвестным key и возвратом назад при уже введенной теме. Убедитесь, что тип обращения сопоставляется с разрешенным вариантом и что тема не перезаписывается; для URL с разными locale используйте тот же контракт значений. Не добавляйте в URL персональные данные или произвольный текст — передавайте контекст обращения только с помощью короткого идентификатора.

[MDN URLSearchParams: спецификация чтения URL-параметров](https://developer.mozilla.org/en-US/docs/Web/API/URLSearchParams)

## Цель — не просто сократить заполнение формы

Цель этой реализации не только в том, чтобы автоматически заполнять поля формы и создавать впечатление более удобного процесса.

Суть — правильно передать контекст, сформировавшийся на странице услуги, в форму обращения и процессы обработки входящих запросов.

| Аспект              | Что нужно улучшить                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------ |
| Пользователь        | Уменьшить необходимость повторно выбирать услугу, которую он изучал                        |
| Форма               | Предварительно выбрать тип обращения и заполнить тему в соответствии с содержанием запроса |
| Принимающая сторона | Упростить определение цели обращения только по его типу                                    |
| Аналитика           | Упростить отслеживание CTA услуги, с которой началось обращение                            |
| Многоязычный путь   | Переводить на URL обращения, соответствующий locale                                        |

Визуально это небольшая мини-CTA, однако проектирование охватывает CTA, URL, форму, переводы, аналитику и процессы обработки обращений.

## Разделить обязанности в компоненте CTA

В конце каждого раздела услуги разместите CTA «Обсудить эту услугу».

В первую очередь следует избегать ручной записи одинаковой генерации ссылок и GA-атрибутов в каждом разделе страницы услуг. Если у вас 7 услуг, одинаковый код появится 7 раз. При изменении текста или спецификации URL легко что-то упустить.

Поэтому мы создали `ServiceSectionActions` для объединения CTA обращений.

```astro
---
import Icon from "./Icon.astro";
import { t, getLocalizedUrl, type Locale } from "../i18n";

interface Props {
  locale: Locale;
  gaLabel: string;
  gaLocation: string;
  serviceKey: string;
}

const { locale, gaLabel, gaLocation, serviceKey } = Astro.props;
const u = (path: string) => getLocalizedUrl(path, locale);
const contactUrl = `${u("/contact/")}?category=service&service=${encodeURIComponent(serviceKey)}#contact-form`;
---

<a
  href={contactUrl}
  class="ac-btn-outline gap-2 text-sm sm:w-auto"
  data-ga-event="cta_click"
  data-ga-label={gaLabel}
  data-ga-location={gaLocation}
  data-ga-destination={contactUrl}
>
  <Icon name="message-circle" class="text-sm" />
  {t(locale, "pages.services.miniCta")}
</a>
```

Этот компонент выполняет следующие 3 задачи:

- Генерирует URL обращения, соответствующий locale
- Добавляет service key в URL-параметры
- Добавляет label и location для аналитики GA

CTA — это точка взаимодействия с пользователем, а значит, не только элемент UI, но и точка измерения. `data-ga-label` и `data-ga-location` сохранены, чтобы позднее можно было узнать, с какой услуги началось обращение.

## Сделать URL-параметры контрактом с формой

Мы решили передавать значения от CTA к форме обращения через URL-параметры.

```txt
/contact/?category=service&service=web#contact-form
```

Здесь важно не помещать в URL отображаемые пользователю формулировки.

Отображаемые формулировки, такие как `Webサイト制作・運用について`, зависят от перевода, вариантов написания и возможного переименования в будущем. В URL помещайте только короткие service key, например `web` или `server`.

| Параметр   | Назначение                                              |
| ---------- | ------------------------------------------------------- |
| `category` | Указывает точку входа для обработки обращения об услуге |
| `service`  | Стабильный key, обозначающий целевую услугу             |
| hash       | Используется для прокрутки к форме обращения            |

Пользователи могут редактировать URL-параметры. Поэтому на стороне формы не используйте значение URL напрямую как отправляемое значение, а сопоставляйте его с существующим option.

## Хранить таблицу классификации на стороне формы

На стороне формы обращения храните классификацию услуг в массиве.

```ts
const serviceCategoryOptions = [
  {
    key: "server",
    value: "サーバー構築・運用について",
    label: t(locale, "pages.contact.formCategoryServiceServer"),
    subject: t(locale, "pages.services.server.title"),
  },
  {
    key: "web",
    value: "Webサイト制作・運用について",
    label: t(locale, "pages.contact.formCategoryServiceWeb"),
    subject: t(locale, "pages.services.web.title"),
  },
];
```

`key`, `value`, `label` и `subject` выполняют разные функции.

| Поле      | Назначение                                                  |
| --------- | ----------------------------------------------------------- |
| `key`     | Стабильный идентификатор для поиска по URL-параметру        |
| `value`   | Тип обращения, который получатель увидит при отправке формы |
| `label`   | Переведенный вариант, отображаемый на экране                |
| `subject` | Название услуги для предварительного заполнения темы        |

На многоязычном сайте `label` переводится с учетом locale. В то же время `value` используется для классификации на стороне получателя, поэтому ему задается стабильное значение на японском языке.

Это решение зависит от продукта. Если CRM или внешняя форма поддерживает многоязычные категории, значение value тоже можно сделать локализованным. Если, как в этом случае, важно упростить процессы обработки входящих обращений, удобнее разделять отображаемую подпись и принимаемое значение.

## Добавить data-атрибуты к option

В select формы выводятся option для отдельных услуг.

```astro
<select id="category" name="category" required>
  <option value="" disabled selected>
    {t(locale, "pages.contact.formCategoryPlaceholder")}
  </option>
  <option value="サービス全般について">
    {t(locale, "pages.contact.formCategoryService")}
  </option>
  {serviceCategoryOptions.map((option) => (
    <option
      value={option.value}
      data-service-key={option.key}
      data-service-subject={option.subject}
    >
      {option.label}
    </option>
  ))}
</select>
```

`data-service-key` используется для сопоставления с URL-параметром `service`. `data-service-subject` используется для формирования темы.

И здесь важно не передавать значение URL напрямую в `category.value`. Всегда выбирайте вариант из option внутри select — так неизвестный service key или некорректное значение не попадут в принимаемое значение.

## Выполнить prefill на стороне клиента

Инициализация формы выполняется небольшим скриптом после загрузки страницы.

```js
function initContactServicePrefill() {
  const form = document.getElementById("contact-form");
  if (!form || form.dataset.servicePrefillInitialized === "true") return;

  form.dataset.servicePrefillInitialized = "true";

  const url = new URL(window.location.href);
  const requestedCategory = url.searchParams.get("category");
  const requestedService = url.searchParams.get("service") || "";
  const category = document.getElementById("category");
  const subject = document.getElementById("subject");

  if (
    requestedCategory === "service" &&
    category instanceof HTMLSelectElement
  ) {
    const serviceOption = Array.from(category.options).find((option) => {
      return option.dataset.serviceKey === requestedService;
    });

    category.value = serviceOption?.value || "サービス全般について";
    category.dispatchEvent(new Event("input", { bubbles: true }));
    category.dispatchEvent(new Event("change", { bubbles: true }));

    if (
      serviceOption &&
      subject instanceof HTMLInputElement &&
      !subject.value.trim()
    ) {
      const template = form.dataset.serviceSubjectTemplate || "{service}";
      const serviceName =
        serviceOption.dataset.serviceSubject ||
        serviceOption.textContent?.trim() ||
        "";
      subject.value = template.replace("{service}", serviceName);
    }
  }
}
```

В реализации важно учитывать следующие 4 пункта:

- Проверять `data-service-prefill-initialized`, чтобы избежать повторной инициализации
- Выполнять обработку только если `category=service`
- Для неизвестного service key использовать переход к общим вопросам об услугах
- Предварительно заполнять тему только если она пуста

Особенно важно последнее условие: только если тема пуста. Если тема уже заполнена из-за возврата пользователя или автозаполнения браузера, произвольное перезаписывание ухудшит пользовательский опыт.

Если в Astro используются View Transitions или клиентская навигация, инициализируйте форму не только при обычной первоначальной загрузке, но и при `astro:page-load`.

```js
document.addEventListener("astro:page-load", initContactServicePrefill);
initContactServicePrefill();
```

## Перейти к форме по hash

В URL CTA добавляется `#contact-form`.

```txt
/contact/?category=service&service=web#contact-form
```

На странице обращения есть FAQ, LINE, описание и другие способы связи помимо формы, поэтому пользователю, пришедшему с CTA услуги, естественнее сразу перейти к форме.

Но если форма инициализируется на стороне формы, нужно уделить немного внимания времени прокрутки. Чтобы прокрутка выполнялась после отображения элемента, используется `requestAnimationFrame`.

```js
if (window.location.hash === "#contact-form") {
  window.requestAnimationFrame(() => {
    form.scrollIntoView({ block: "start" });
  });
}
```

Переход к форме — небольшое изменение поведения, но если намерение CTA и положение формы на экране расходятся, пользователь теряется. При проектировании пути нужно комплексно учитывать URL, первоначальный выбор и положение прокрутки.

## Решить не добавлять hidden-поля

На этот раз мы не добавляли hidden-поле `相談対象サービス`.

Причина в том, что мы хотели, чтобы целевую услугу можно было определить только по типу обращения.

При добавлении полей увеличивается и число вопросов, которые нужно согласовать:

- Выводить ли поле в уведомлении по электронной почте
- Добавлять ли столбец в административную панель или электронную таблицу
- Повлияет ли оно на существующий шаблон автоответа
- Использовать ли его в интеграции с CRM или в webhook
- Как разделять отображаемые на разных языках названия и принимаемые значения

Если необходимую информацию можно представить в существующих полях, процессы будут стабильнее, если не добавлять новые. В этом случае мы разделили только `お問い合わせ種別` на общие вопросы об услугах и типы обращений по отдельным услугам, чтобы получатель мог их различать.

Разумеется, если нужно одновременно выбрать несколько услуг, сохранить ID рекламной кампании или использовать отдельное поле в CRM, можно принять решение о добавлении hidden-полей.

## Подход к многоязычному сайту

При создании такого пути на многоязычном сайте, чтобы избежать путаницы, разделяйте значения на 3 категории.

| Тип                  | Пример                         | Зависит от locale    |
| -------------------- | ------------------------------ | -------------------- |
| URL key              | `web`, `server`, `aceserver`   | Нет                  |
| Отображаемая подпись | `About Website Design` и т. п. | Да                   |
| Принимаемое значение | `Webサイト制作・運用について`  | Зависит от процессов |

URL key лучше не переводить: это важно для обмена ссылками, аналитики и сопоставления на стороне формы.

Отображаемую подпись обязательно переводите, ведь именно ее пользователь видит в форме.

Принимаемое значение выбирайте в соответствии с процессами. Здесь мы использовали стабильное значение на японском языке. Если отдельно проектировать локализованные подписи и внутренние процессы после получения обращения, форму проще обслуживать.

О процессе перевода мы также рассказали в статье [Как вести многоязычный блог в Sveltia CMS](/blog/copilot-translation-pipeline/).

## Проверить сгенерированный HTML

Для такой реализации недостаточно проверять только компоненты. Убедитесь, что после build в HTML действительно выводятся ссылки и option.

На этот раз проверялись следующие аспекты:

- В `/services/` есть 7 CTA для отдельных услуг
- Каждая CTA содержит `?category=service&service=...#contact-form`
- В `/contact/` выведено 7 option с `data-service-key`
- Выведены общие вопросы об услугах и типы обращений для отдельных услуг
- Не выведено hidden-поле `相談対象サービス`

Например, с помощью `rg` можно проверить сгенерированный HTML.

```powershell
rg -n "category=service&service=.*#contact-form" dist\services\index.html
rg -n "data-service-key" dist\contact\index.html
rg -n "相談対象サービス" dist\contact\index.html
```

Последняя проверка нужна, чтобы убедиться, что не появились элементы, которых быть не должно. При доработке формы следует проверять не только добавленные элементы, но и то, что мы решили не добавлять.

## Разделение ролей с AI-чатом

Этот путь сочетается с [техническим проектированием AI-чата для обращений](/blog/astro-ai-contact-chat/). Однако роли у них разные.

| Путь       | Что получается лучше всего                                     |
| ---------- | -------------------------------------------------------------- |
| AI-чат     | В диалоге определить, с какой услугой обратиться               |
| CTA услуги | Передать в форму контекст услуги, которую изучает пользователь |
| Форма      | Получить официальное содержание обращения и сохранить запись   |

AI-чат хорошо подходит, когда пользователь еще не определился. Напротив, если он прочитал страницу услуги и решил «Обсудить эту услугу», естественнее направить его сразу в форму, не начиная диалог.

Добавляя новые пути, важно не наделять их всех одной и той же ролью. Используйте диалог, CTA и форму в зависимости от состояния пользователя.

## Итоги

Реализация передачи контекста со страницы услуги в форму обращения дает эффект, который может быть больше, чем кажется по ее внешнему виду.

В этом проектировании важны следующие моменты:

- Вынести CTA в компонент и объединить генерацию URL и атрибуты аналитики
- Помещать в URL стабильный service key, а не отображаемую формулировку
- Сопоставлять service key с option на стороне формы
- Разделять принимаемое значение, отображаемую подпись и название услуги для темы
- Для неизвестного service key переходить к общим вопросам об услугах
- Предварительно заполнять тему только если она пуста
- Не добавлять hidden-поля и классифицировать обращения по их типу
- После build проверять количество ссылок и option в сгенерированном HTML, а также отсутствие ненужных полей

Улучшение формы обращения — это не просто сокращение числа полей. Сохранение контекста, который изучал пользователь, вплоть до принимающей стороны упрощает фактическую обработку обращений.

## Дополнение от 2026 года, 10-го месяца, 6-го числа: от приема обращения до управленческой записи

В анонимизированной доработке интеграции мы рассматривали прием обращения, внесение сведений в историю и задачи CRM, а также завершение обработки ответственным сотрудником как отдельные состояния. Ввод URL и путь обращения проверяются, а значения пути сопоставляются со стабильным enum. Одного знания URL административной панели недостаточно, чтобы получить право изменять историю или задачи.

В API также проверяются пользователь и его право на операцию, а сведения о клиентах не включаются в публичный поиск или материалы публичных ответов AI. Завершение реализации приема обращения или записи не означает, что была подтверждена сквозная обработка от контакта с реальным клиентом до завершения работы.

Предварительное заполнение формы и ввод самим пользователем различаются; для обращений, по которым нужно перезвонить, обязательный фиксированный вариант предпочтительного канала связи передается в последующую задачу. Согласуются обязательные условия в UI и API, права сотрудников на просмотр и добавление записей, а после изменения DB проверяются schema и constraint. Необходимые проверки production также отделяются от копирования всех DB реальных клиентов в среду разработки.

Если ссылка в ответе ИИ остаётся простой строкой, последовательно пропустите один и тот же ввод через разбор, проверку URL и построение DOM, чтобы определить, на каком этапе возникает сбой. Для отображения текста используйте текстовый API, например [MDN: textContent](https://developer.mozilla.org/en-US/docs/Web/API/Node/textContent), и не смешивайте решение о преобразовании текста в ссылку с интерпретацией HTML: это отправная точка при доработке существующего чата.

Если попросить ИИ-чат ответить: «Подробнее см. [список услуг](/services/)», ссылка может не отобразиться, а строка Markdown останется без изменений.

На сайте Acecore в ответы ИИ-чата для обращений тоже попали Markdown-ссылки с пробелами перед URL или после него, поэтому в [PR с исправлением отображения Markdown-ссылок в ИИ-чате](https://github.com/acecore-systems/acecore-net/pull/99) мы скорректировали рендерер.

В этой статье на примере этого небольшого исправления изложены принципы безопасного преобразования ответов ИИ в DOM.

## Ответы ИИ — это не доверенный HTML

Прежде всего, ответы ИИ следует рассматривать как текст, а не как HTML.

В интерфейсе чата обычно хочется поддерживать ссылки, полужирный текст и маркированные списки. Однако если напрямую вставить ответ в `innerHTML`, браузер будет интерпретировать строку, выданную моделью.

Не нужно реализовывать весь Markdown. Достаточно извлекать только те элементы, которые нужны в чате, и создавать только безопасные узлы DOM.

## Проблема не только в пробелах

Непосредственной причиной этой ошибки стала ссылка следующего вида.

```md
[サービス一覧](/services/)
```

Для человека смысл такого Markdown понятен, но регулярное выражение, которое ищет в URL-части строку без пробелов, не найдёт совпадение.

До исправления использовалась такая логика.

```js
/\[([^\]]+)\]\(([^)\s]+)\)/;
```

`[^)\s]+` не допускает пробелы, поэтому не может извлечь `( /services/ )` как ссылку. Поэтому разрешим пробелы перед URL и после него внутри скобок, а сам URL позже обработаем с помощью trim.

```js
/\[([^\]]+)\]\(\s*([^)]+?)\s*\)/;
```

Важно не ограничиваться ослаблением регулярного выражения. После этого обязательно нужно выполнить нормализацию и проверку безопасности.

## Сначала применяйте trim к href, а затем проверяйте его

Порядок создания ссылок всегда один и тот же.

1. Извлечь из Markdown label и raw href
2. Применить `trim()` к raw href
3. Проверить href после trim по списку разрешённых адресов
4. Создать `<a>` только в том случае, если URL разрешён

```js
const href = String(rawHref || "").trim();

if (label && isSafeMarkdownHref(href)) {
  const link = document.createElement("a");
  link.href = href;
  link.rel = "noopener noreferrer";

  if (/^https?:\/\//i.test(href)) {
    link.target = "_blank";
  }

  link.textContent = label;
  parent.appendChild(link);
}
```

Проверять нужно фактически вставляемое в DOM значение, а не исходное значение до `trim()`. Если проверенное и отображаемое значения отличаются, смысл проверки безопасности ослабевает.

## Список разрешённых адресов зависит от продукта

Набор URL, по которым ИИ-чат может направлять пользователя, различается от сайта к сайту.

Для ИИ-чата Acecore для обработки обращений мы ограничили список примерно следующим набором.

| Тип                | Пример                    | Решение                                           |
| ------------------ | ------------------------- | ------------------------------------------------- |
| Внутренний путь    | `/services/`              | Разрешить                                         |
| Тот же origin      | `https://acecore.net/...` | Разрешить                                         |
| Официальный LINE   | `https://lin.ee/...`      | Разрешить, поскольку назначение понятно           |
| mailto             | `mailto:info@acecore.net` | Разрешить только необходимые фиксированные адреса |
| tel                | `tel:0120987370`          | Разрешить только необходимые фиксированные номера |
| Другие внешние URL | Произвольный URL          | По умолчанию не превращать в ссылки               |

Пример реализации выглядит так.

```js
function isSafeMarkdownHref(rawHref) {
  const href = String(rawHref ?? "").trim();
  if (!href || /[\u0000-\u001f\u007f\\]/u.test(href)) return false;
  if (href === "mailto:info@acecore.net" || href === "tel:0120987370") {
    return true;
  }

  try {
    if (href.startsWith("/")) {
      if (href.startsWith("//")) return false;
      const url = new URL(href, window.location.origin);
      return (
        url.origin === window.location.origin && !url.username && !url.password
      );
    }

    const url = new URL(href);
    return (
      url.protocol === "https:" &&
      !url.username &&
      !url.password &&
      !url.port &&
      [
        window.location.origin,
        "https://acecore.net",
        "https://lin.ee",
      ].includes(url.origin)
    );
  } catch {
    return false;
  }
}
```

Эту функцию следует адаптировать для каждого сайта. На карьерном сайте можно разрешить платформы с вакансиями, в интернет-магазине — платёжные сервисы или отслеживание доставки, а в SaaS-сервисе — документацию или страницу статуса.

## Запрещённые ссылки нужно оставлять текстом

Обработка ссылок, которые не прошли проверку безопасности, — тоже часть проектирования.

Для ИИ-помощника по обращениям удобнее не удалять Markdown-ссылку, которую нельзя преобразовать в ссылку, а оставить её исходным текстом. Так у пользователя сохраняется контекст, а разработчик может проверить, что именно выдал ИИ.

Иными словами, парсер отвечает не только за создание безопасных ссылок, но и за вывод содержимого обычным текстом, если безопасно создать ссылку не удалось.

## Подготовьте тестовые случаи заранее

Проблемы в таком рендерере легко упустить, если проверять только штатные сценарии.

Как минимум проверьте следующие случаи.

| Ввод                                | Ожидаемый результат                               |
| ----------------------------------- | ------------------------------------------------- |
| `[サービス一覧](/services/)`        | Превращается во внутреннюю ссылку                 |
| `[サービス一覧]( /services/ )`      | Обрезается trim и становится внутренней ссылкой   |
| `[LINE]( https://lin.ee/example )`  | Открывается как внешняя ссылка                    |
| `[危険](javascript:alert(1))`       | Не превращается в ссылку                          |
| `[外部](https://example.com/)`      | Не превращается в ссылку, если URL не разрешён    |
| `[壊れたリンク](/services/`         | Отображается как текст                            |
| `` `code` と [link]( /contact/ ) `` | Элемент кода и ссылка отображаются по отдельности |

В PR #99 мы подтвердили, что `[サービス一覧]( /services/ )`, `[サービス一覧](/services/)` и `[LINE]( https://lin.ee/DjIrdqj )` обрабатываются как один и тот же URL.

## Не реализуйте весь Markdown

Набор элементов Markdown, необходимых в ИИ-чате, можно ограничить.

- Абзацы
- Маркированные списки
- Полужирное начертание
- Встроенный код
- Ссылки

Если добавить поддержку таблиц, изображений, HTML, сносок и сложной иерархии заголовков, ответственность рендерера резко возрастёт. Для чата достаточно понятно и удобно направлять пользователя.

При необходимости можно выбрать проверенную библиотеку Markdown. Но и в этом случае отдельно нужно решить, разрешать ли HTML, как ограничивать URL и какие атрибуты добавлять к внешним ссылкам.

## Итог

Отображение Markdown-ссылок в ИИ-чате может показаться небольшой косметической правкой. Однако на деле это вопрос проектирования границы доверия к ответам ИИ.

При реализации важно следующее.

- Рассматривать ответы ИИ как текст, а не HTML
- Превращать в DOM только необходимые элементы Markdown
- Допускать пробелы перед URL и после него в Markdown-ссылках
- Проверять безопасность href после trim
- Пропускать по списку разрешённых адресов только внутренние и необходимые внешние URL
- Оставлять запрещённые ссылки обычным текстом
- Тестировать некорректный Markdown и опасные URL

Чем активнее ИИ используется для навигации по сайту, тем важнее способ отображения текста ответов. Удобную поддержку Markdown и безопасное управление ссылками нужно реализовывать вместе, в рамках одного решения.

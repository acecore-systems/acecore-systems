При первом запуске AI-чата на статическом сайте ограничьте его ответами на опубликованные FAQ, а официальные запросы и расчёт стоимости направляйте в форму. Серверные подключения проверьте по документации [Cloudflare Pages: Bindings](https://developers.cloudflare.com/pages/functions/bindings/). Приведённая ниже проверка URL — упрощённый исторический пример: при реализации используйте разбор URL и список разрешённых адресов из связанной статьи, а не только проверку начала строки.

Добавить AI-чат для обращений на сайт несложно. При эксплуатации важнее не только возможности модели, но и то, на какие вопросы ей разрешено отвечать, куда направлять посетителей, какие URL показывать и как ограничить расходы на API.

Acecore добавила AI-чат для обращений на статический сайт Astro + Cloudflare Pages. Основа реализации — [PR с AI для обращений и потоком переводов, ограниченным CMS](https://github.com/acecore-systems/acecore-net/pull/98). Позднее безопасный вывод Markdown-ссылок в ответах AI был доработан в [отдельном PR](https://github.com/acecore-systems/acecore-net/pull/99). Подробности вынесены в статью [Техническое решение для безопасного вывода Markdown-ссылок в ответах AI-чата](/blog/ai-chat-markdown-link-safety/).

Здесь архитектура представлена как решение, которое можно перенести на другие статические сайты. Принцип подходит и для других фронтендов: разделить обязанности клиента, границы API, промпта и компонента вывода.

## Общая архитектура

Решение состоит из 3 простых слоёв.

| Слой                 | Роль                                                                          |
| -------------------- | ----------------------------------------------------------------------------- |
| Виджет чата          | Интерфейс, ввод, выбранный язык, минимальная история и вывод Markdown         |
| `/api/ai-contact`    | Проверка ввода и Origin, ограничение частоты, создание промпта и вызов OpenAI |
| OpenAI Responses API | Формирование ответа на основе информации сайта и контекста диалога            |

Браузер не вызывает OpenAI API напрямую по 3 причинам:

- Ключ API не попадает в браузер.
- Модель, промпт и контекст сайта можно обновлять на сервере.
- Ограничения длины ввода и частоты, проверка Origin и обработка ошибок сосредоточены в 1 месте.

В Astro + Cloudflare Pages границу API можно реализовать как `/api/ai-contact` в Cloudflare Pages Functions. В Next.js её заменит Route Handler, а в Hono или Express — API route.

## Минимальный контракт endpoint

В API чата следует передавать как можно меньше данных.

```ts
type ContactAiRequest = {
  message: string;
  locale: "ja" | "en" | "zh-cn" | "es" | "pt" | "fr" | "ko" | "de" | "ru";
  history?: Array<{
    role: "user" | "assistant";
    content: string;
  }>;
};

type ContactAiResponse = {
  answer: string;
};
```

Мы решили не отправлять в AI-чат имя, адрес электронной почты, телефон, название компании и другие данные из формы. Чат предназначен не для сбора персональной информации, а для помощи посетителю в выборе услуги и способа обращения.

История тоже не передаётся целиком: достаточно нескольких последних сообщений, а длина каждого сообщения ограничивается до установленного числа символов на 1 сообщение. Это помогает сдерживать размер промпта и расходы на API.

## Управление вводом и вызовом на сервере

Cloudflare Pages Function выполняет следующие действия вместе.

```ts
export async function onRequestPost({ request, env }: PagesFunction<Env>) {
  assertSameOrigin(request);
  assertRateLimit(request);

  const body = await request.json();
  const message = validateMessage(body.message);
  const locale = validateLocale(body.locale);
  const history = trimHistory(body.history);

  const prompt = buildContactPrompt({
    locale,
    message,
    history,
    siteContext: buildPublicSiteContext(locale),
  });

  const answer = await callOpenAIResponsesApi({
    apiKey: env.OPENAI_API_KEY,
    model: env.OPENAI_MODEL,
    prompt,
  });

  return Response.json({ answer });
}
```

Главное — до вызова OpenAI проверить и сократить входные данные. AI API тарифицирует полученный ввод; если пропускать длинные тексты, ненужную историю и непрерывные обращения со сторонних сайтов, эксплуатация станет нестабильной прежде, чем возникнут функциональные проблемы.

Переменная окружения `OPENAI_MODEL` упрощает смену модели и проверку в preview-среде. `OPENAI_API_KEY` хранится исключительно в серверных переменных окружения.

Доставка через Cloudflare Pages и подход к CSP рассмотрены в статье [Безопасная раздача статического сайта с Cloudflare Pages](/insights/cloudflare-pages-security/).

## Явный контекст из информации сайта

Для сайта такого масштаба не обязательно сразу внедрять векторную базу или RAG. Сначала проще и в разработке, и в эксплуатации структурировать основные сведения опубликованного сайта и передать их в промпт.

Например, сервер может собрать:

- описание компании и услуг;
- аудиторию каждой услуги, примеры запросов и связанные URL;
- ответы из FAQ;
- правила выбора между формой, LINE, электронной почтой и телефоном;
- темы, по которым AI не должен делать категоричных утверждений, например цены, договоры и сроки;
- внутренние URL для каждого языка.

Важно передать модели информацию, которую сайт вправе использовать в ответах, а не просить её отвечать на основе предположительно известных ей фактов.

```ts
function buildPublicSiteContext(locale: Locale) {
  return {
    services: [
      {
        name: "Web制作",
        summary: "コーポレートサイト、採用サイト、LPの制作相談に対応",
        url: localizePath("/services/web-production/", locale),
      },
      {
        name: "サーバー運用",
        summary: "クラウド、VPS、監視、バックアップ設計の相談に対応",
        url: localizePath("/services/server-operations/", locale),
      },
    ],
    contact: {
      form: localizePath("/contact/", locale),
      line: "https://lin.ee/...",
      emailPolicy: "フォームが使えない場合や補足が必要な場合だけ案内する",
      phonePolicy: "急ぎの確認が必要な場合だけ案内する",
    },
  };
}
```

Пока страниц немного, этого достаточно. С ростом числа страниц, частоты обновлений и поисковых требований можно добавить слой поиска с Pagefind, JSON из CMS, D1 или Vectorize.

## В промпте важнее правила, чем формулировка ответа

В промпте для AI-чата нужно прежде всего определить допустимые темы и запреты, а не только попросить модель писать естественным языком.

```txt
あなたはこのサイトの問い合わせ案内AIです。
公開済みサイト情報だけを根拠に回答してください。

ルール:
- 料金、契約、納期、保証を断定しない
- 詳細見積りや正式な相談は問い合わせフォームへ案内する
- 短い確認やSchoolsに関する相談はLINEも案内する
- メールと電話は、ユーザーが直接連絡を求めた場合だけ案内する
- 内部リンクは現在のlocaleに合うURLを使う
- わからない場合は、推測せずフォームへ案内する
```

Типичная ошибка — модель стремится представить услугу в выгодном свете и отвечает слишком категорично. На вопросы «Сколько это стоит?», «К какому сроку вы выполните работу?» или «Вы точно сможете помочь?» следует дать общую информацию и направить за официальным ответом в форму.

Дело не только в юридических вопросах: стоимость и сроки нельзя определить до выяснения требований. В промпте следует указать границы ответов, за которые можно отвечать при эксплуатации, а не просто удобные для продаж формулировки.

## Разделение каналов обращения

AI-чат не заменяет форму. На странице контактов удобно распределить задачи так:

| Канал           | Роль                                                                                         |
| --------------- | -------------------------------------------------------------------------------------------- |
| FAQ             | Заранее ответить на частые вопросы на странице                                               |
| AI-чат          | В диалоге помочь выбрать услугу, контакт и связанные страницы                                |
| LINE            | Короткие консультации, обращения о Schools и простые уточнения                               |
| Форма           | Запросы стоимости, разработка, партнёрство, найм и другие обращения, которые нужно сохранить |
| Прямые контакты | Дополнения после формы или срочные уточнения                                                 |

Если AI связывает обзорные материалы вроде [страницы услуг](/services/) с конкретными каналами на [странице контактов](/contact/), посетителю не придётся заново искать нужную страницу.

Подход применим и к BtoB-сайтам, сайтам студий и школ, а также поддержке SaaS. Его проще внедрить, если чат помогает выбрать следующую страницу или канал связи, а не пытается полностью завершить обращение.

## Сохранение URL для каждого языка

На многоязычном сайте нужно учитывать не только язык ответа AI, но и язык URL, на который ведёт ссылка.

Например, на вопрос с английской страницы следует ответить по-английски и использовать локализованный URL услуги, например `/en/services/`. Для японской страницы используется `/services/`.

Надёжнее определять адрес серверной функцией, чем поручать это промпту.

```ts
function localizePath(path: string, locale: Locale) {
  if (locale === "ja") return path;
  return `/${locale}${path}`;
}
```

Если ответ AI вернёт пользователя на японский URL, многоязычная навигация нарушится. Основа работы с многоязычным блогом и переводами описана в статье [Как вести многоязычный блог с Sveltia CMS](/blog/copilot-translation-pipeline/).

## Проверка Origin и ограничение частоты

`/api/ai-contact` — публичный API, поэтому следует как минимум проверять Origin и ограничивать длину ввода, историю и частоту запросов.

Если заголовок `Origin` присутствует, проверка Origin сопоставляет хост источника запроса с хостом API. Это снижает риск нежелательных вызовов с других сайтов.

```ts
function assertSameOrigin(request: Request) {
  const origin = request.headers.get("Origin");
  if (!origin) return;

  const requestUrl = new URL(request.url);
  const originUrl = new URL(origin);

  if (originUrl.host !== requestUrl.host) {
    throw new Response("Forbidden", { status: 403 });
  }
}
```

Для начала полезно даже простое ограничение по IP. В Cloudflare для идентификации можно использовать `CF-Connecting-IP`, `X-Forwarded-For` или `CF-Ray`.

Однако ограничение в памяти не сохраняется между несколькими изолятами и перезапусками. Оно подходит как начальная мера для небольшого сайта, но при росте нагрузки надёжнее перейти к Cloudflare WAF, Turnstile, KV, D1 или Durable Objects.

Организация CMS для обновления контента описана отдельно в [руководстве по внедрению Sveltia CMS](/blog/cms-selection-and-turnstile/). Защиту форм и комментариев от ботов, например с Turnstile, следует рассматривать как отдельный слой. Архитектура комментариев только на Cloudflare приведена в статье [Как добавить комментарии в блог Astro, используя только Cloudflare](/blog/cloudflare-only-blog-comments/).

## Вывод Markdown-ссылок по списку разрешённых адресов

Ссылки в ответах AI полезны для навигации по услугам, но передавать Markdown в HTML без обработки не следует.

Интерфейс чата преобразует в DOM только разрешённые элементы:

- абзацы;
- маркированные списки;
- жирный текст;
- встроенный код;
- Markdown-ссылки.

Дополнительно ограничиваются назначения ссылок:

- пути внутри того же сайта, например `/services/`;
- текущий origin;
- `https://acecore.net`
- официальный LINE;
- при необходимости `mailto:info@acecore.net`;
- при необходимости `tel:0120987370`.

Перед проверкой URL обязательно применяется `trim()`. Модель может вернуть пробелы вокруг адреса, как в примере `[サービス一覧]( /services/ )`.

```ts
function sanitizeHref(rawHref: string, currentOrigin: string) {
  const href = rawHref.trim();

  if (href.startsWith("/")) return href;
  if (href.startsWith(`${currentOrigin}/`)) return href;
  if (href.startsWith("https://acecore.net/")) return href;
  if (href.startsWith("https://lin.ee/")) return href;
  if (href === "mailto:info@acecore.net") return href;
  if (href === "tel:0120987370") return href;

  return null;
}
```

Проще надёжно обрабатывать только нужные в чате элементы, чем реализовывать всю спецификацию Markdown. Даже если нужны произвольные внешние URL, следует как минимум использовать список разрешённых доменов и `rel="noopener noreferrer"`.

## Проверка локально, в preview и в production

Локальные Astro dev и preview не полностью совпадают со средой Cloudflare Pages Functions. Без `OPENAI_API_KEY` ответы AI недоступны, поэтому проверьте резервное состояние интерфейса и отображение ошибок.

В Pages preview или production проверьте следующее:

- `/api/ai-contact` вызывается методом POST;
- `OPENAI_API_KEY` и `OPENAI_MODEL` настроены;
- запрос с другим Origin отклоняется;
- длина ввода и число сообщений истории ограничены;
- язык ответа соответствует выбранному языку интерфейса;
- внутренние ссылки ведут на URL с нужной локалью;
- AI не делает категоричных утверждений о стоимости и договорах;
- электронная почта и телефон не показываются постоянно;
- Markdown-ссылки преобразуются только в безопасные URL.

Проверки AI-интеграции не завершаются после 1 успешного вопроса. Отдельно проверьте неожиданные вопросы, длинный ввод, вопросы с английской страницы, запросы прямых контактов и вопросы о цене.

## Журналы и эксплуатационные показатели

После публикации AI-чата важно проверять журналы. Как минимум стоит отслеживать:

- долю ошибок API;
- число срабатываний ограничения частоты;
- среднее число сообщений на 1 обращение;
- число переходов к форме или в LINE;
- число случаев, когда AI не ответил и направил пользователя к форме;
- использование по языкам.

Если сохраняется содержание разговоров, сначала необходимо определить порядок работы с персональными данными. Безопаснее начать с подсчёта событий и ошибок без сохранения текста сообщений.

## Границы статьи

Здесь мы рассмотрели только техническую архитектуру AI-чата для обращений. Связанный механизм передачи контекста услуги из её страницы в форму описан отдельно: [Техническое решение для передачи контекста из CTA услуги в форму обращения](/blog/service-cta-contact-prefill/).

Темы различаются:

- AI-чат помогает разобраться в вопросе в диалоге и безопасно направляет пользователя;
- CTA конкретной услуги передаёт в форму контекст просматриваемой услуги.

Первое касается AI, границы API, промпта и безопасного вывода. Второе — удобства формы и навигации. Раздельное описание проще читать и связывать внутренними ссылками.

## Итоги

При добавлении AI-чата для обращений к статическому сайту важнее сначала спроектировать границу API и управление ответами, чем интерфейс чата.

В этой реализации особенно полезны следующие решения:

- вызывать OpenAI API из Cloudflare Pages Function, а не из браузера;
- минимизировать вход endpoint и ограничить историю и длину сообщений;
- формировать информацию сайта и URL для каждого языка на сервере;
- указывать в промпте, какие утверждения AI может и не может делать;
- разделить роли формы, LINE и прямых контактов;
- проверять Origin и ограничивать частоту запросов;
- удалять пробелы вокруг URL и выводить Markdown-ссылки по списку разрешённых адресов.

AI-чат для обращений вполне можно реализовать на статическом сайте. Главное при внедрении — помочь посетителю безопасно выбрать следующее действие.

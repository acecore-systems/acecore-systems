## Не дублировать проверки при push и PR

В другой системе протоколирования совещаний обычный CI и проверка Rust parity запускались как при push в рабочую ветку, так и при PR. Запуск по push ограничили веткой main, сохранили проверки PR и предусмотрели ручной запуск для проверки до создания PR. Условия запуска релиза в production не изменились.

По результатам внутреннего исследования, в месяце 11 было 97 запусков по push, для которых проверки PR также прошли успешно; их суммарное время на Linux-раннерах составило 342 мин. Это время запусков, отобранных для изучения дублирования, а не фактически сэкономленное после изменения время или сумма в счёте. Прежде чем ограничивать условия запуска, нужно проверить, как будут проверяться изменения без PR и не остановятся ли обязательные проверки и релизы. Условия push и pull_request можно проверить в документации по [событиям GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

## Результаты измерений задания и условия

При сравнении одного и того же коммита, зафиксированном во внутреннем журнале изменений, задание Android заняло 16 мин 20 с при первом запуске и 6 мин 16 с при повторном, включая восстановление. Были повторно использованы 194 задач Gradle, а проверки x86_64 и arm64-v8a и создание APK также прошли успешно. Сохранение при первом запуске заняло 34 с, восстановление при повторном — 62 с, а размер тестового кеша составил около 1.81 GB.

| Показатель       | Первый запуск    | Повторный запуск     |
| ---------------- | ---------------- | -------------------- |
| Задание Android  | 16 мин 20 с      | 6 мин 16 с           |
| Операция с кешем | Сохранение: 34 с | Восстановление: 62 с |

Эта 1 пара запусков измерялась с кешем, предназначенным только для PR. В итоговой конфигурации общий кеш сохраняет только main, а PR восстанавливают его в режиме только для чтения. Мы не измеряли, достигается ли такое же сокращение времени для всех PR в итоговой конфигурации и уменьшается ли сумма в счёте. Результаты также зависят от среды выполнения и частоты совпадений кеша.

## Определить условия повторного использования и безопасного сохранения

[Кеш сборки Gradle](https://docs.gradle.org/current/userguide/build_cache.html) определяет возможность повторного использования по входным и выходным данным задач. Неточное объявление входных данных задачи может привести к использованию устаревших выходных данных, поэтому сначала сравните результаты чистого запуска, артефакты и результаты тестов. Также проверьте, что кеш инвалидируется ожидаемым образом при изменении зависимостей или настроек сборки.

Ограничьте круг субъектов, которым разрешено сохранение, чтобы недоверенные изменения не обновляли общий кеш. Для [кеша зависимостей GitHub Actions](https://docs.github.com/en/actions/concepts/workflows-and-actions/dependency-caching) действуют ограничения доступа и особые условия использования. Не храните секреты в кеше; отслеживайте его размер, время сохранения и восстановления, а также общую продолжительность задания.

Сначала выберите 1 задание и зафиксируйте артефакты и время первого и повторного запусков одного коммита. Даже если время сократилось, отдельно проверьте, что сборка успешно выполняется при других изменениях и отсутствии кеша. Дата проверки: 2026-11-17.

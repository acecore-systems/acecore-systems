# 技術記事の執筆・参考リンク・公開方針

Acecore Systemsの技術解説は、読者が自分の業務やアプリに技術を活用できるように書く。検索で見つけてもらうために、課題に答えるタイトルと本文、具体例、確認できる出典を重視する。日本語を正本とし、この方針を新規記事と改訂に適用する。

## タイトルと導入

最初に、想定する読者と「何を知りたくて検索するか」を一文で定める。タイトルには技術名と、本文で答える用途・方法・比較の軸を自然に含める。内容を正確に表し、誇張や検索語の詰め込みを避ける。

たとえば、分類や判定への適用を説明する記事なら「OpenAI Decisions API活用術：分類・判定の使いどころと実装のコツ」のように、得られる知識を示す。自社の導入記録を扱う場合も、読者が使える知識をタイトルと冒頭で伝える。

descriptionと冒頭では、対象の課題、紹介する使い方、読後に判断・実装できることを示す。公開済みの類似記事を確認し、同じ説明を重複させるより、今回の具体例や比較から得られる知識を加える。

## 本文の組み立て

次の流れを基本とし、題材に合わせて調整する。

1. 何に使えるか、どの課題を解決できるかを示す。
2. 具体的な活用法、要求例、実装手順を説明する。
3. 実例や比較から、効果と適用条件を説明する。
4. 費用、待ち時間、品質、向かない用途を判断材料にする。
5. 読者が最初の一件を試す手順と参考資料を用意する。

見出しは、読者が探したい用途や疑問から付ける。作業順の記録やPR番号の列挙を本文の中心にせず、実装事例を活用法の根拠として使う。コード・図・表は、理解や比較に役立つものを選ぶ。

実測値、推定値、架空の説明例、コードの経路確認、実運用での確認を区別する。数値には条件や標本数を添え、仕様・料金には確認日を記す。公開を控える指定がある運用詳細、個人情報、認証情報は、本文だけでなく図や集計データにも含めない。

## 参考URLと関連リンク

関連する参考URLへの外部リンクを、SEO改善の標準施策として積極的に掲載する。仕様・料金・制約の説明には、公式ドキュメントや一次資料を優先してリンクする。GIGAZINEなどの解説記事は、日本語で概要をつかむための補助資料として、何を読めるか分かる説明を添える。記事で用いた比較データや、理解に役立つ自サイトの記事にもリンクする。

リンク先を実際に開き、本文を支える箇所と公開状態を確認する。本文中の主張の近く、または`linkCards`へ、対象が分かる短いリンク名で置く。参考URLの件数を目的にせず、読者が確かめたり次の理解へ進んだりできる資料を選ぶ。ニュース記事の要約だけで完結させず、自分たちの実例・比較・判断を加える。

参考リンクは、検索意図に合った解説、独自の実例、関連する内部リンクと合わせて記事を改善するために使う。通常の参考リンクへ一律に`nofollow`を付けず、広告・提供を受けたリンクや投稿者が挿入するリンクは、Googleの該当指針に従って扱う。

## 日本語公開と多言語化

新規記事は日本語をレビューして先に公開できる。未完成の8言語は`src/i18n/translation-state.json`の`pendingInsights`へ宣言し、日本語を改訂したら対応するsource hashを更新する。既存の翻訳済み範囲の整合性は引き続き検証する。

公開済みの記事を改訂する場合は、変更したタイトル・description・本文・参考リンクを既存の8言語にも反映し、翻訳状態と同じPRでレビューする。日本語だけを更新して、古い翻訳を最新版として扱わない。全言語を揃えた改訂では、整形後の正本に対応するsource hashを記録する。

現在の自動処理は夜間限定ではない。日本語sourceの`main`へのpushから15分待ち、最新の`main`でOpenAI Batchを投入する。完了結果の回収は毎時2・17・32・47分を予定している。Actionsの開始時刻とBatchの完了時刻には遅れがあり、投入と公開完了を区別する。

回収した翻訳は、現在のsource hash、保護した数値・コード・URLを検証し、専用BotのPRを経てCIと自動マージで公開する。古いsourceの結果や検証に失敗した翻訳は公開しない。公開済みの言語だけを言語切替、hreflang、RSS、サイトマップへ掲載する。

詳細は[READMEの翻訳運用](../../README.md#cms)、[Batch投入](../../.github/workflows/submit-openai-translation-batch.yml)、[結果回収](../../.github/workflows/collect-openai-translation-batch.yml)、[翻訳PRのマージ](../../.github/workflows/merge-openai-translation-pr.yml)を参照する。

## 公開時の確認

記事と翻訳状態を整形し、コンテンツ・i18n・ビルドの既存検証を通す。タイトル・description・見出し・参考リンクをレビューし、GitHub連携の本番公開後に記事本文、記事一覧、RSS、サイト内検索への反映を確認する。SEO metadataや構造化データの検証は既存のビルドで行う。

公開後の改善には、取得できるSearch Consoleの検索語・表示回数・クリック率を使う。確認していない流入増加や検索順位の改善は成果として主張しない。公開日を維持し、実質的な改訂時に更新日を変える。
